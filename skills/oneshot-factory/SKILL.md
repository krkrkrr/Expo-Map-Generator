# ワンショット・ファクトリー

非エンジニアの **1 回の入力** から、**バグなく動く成果物** までを、途中で人に聞かずに作る。

このスキルが解く問題は 2 つだけである。

1. **ゴールの言語化が足りない。** 非エンジニアは要件を書けない。だが具体例に「違う」とは言える。
2. **少なくとも、バグなく動くこと。** そのためにテストシナリオを網羅し、網羅したことを機械で示す。

> バグは 2 種類ある。**実装のバグ**（仕様どおりに動かない）はテストで潰せる。
> **仕様のバグ**（欲しい物と違う）はテストでは潰せない。入口と合議と暗黙要件カタログで減らし、
> 残りは最終報告で利用者に見せる。**この 2 つを混同しない。**

## 前提スキル

- `ddd-bdd-tdd-flow` — 内部の開発手順。本スキルはこれを **autonomous モード** で回す（ステージ 3）
- `tj-loop` — あれば監督に使う（ステージ 6）。無ければ同じ規則を `/loop` で回す
- `unresolved-questions` / `adr-writing-ja` — あれば書式はそれに従う

`ddd-bdd-tdd-flow`、`unresolved-questions`、`adr-writing-ja`、`okf-open-knowledge-format`、`playwright-test`、`external-api-tos-check` は同じプラグインに同梱している（`<このスキルのディレクトリ>/../<名前>/SKILL.md`）。
`tj-loop` は同梱していない。無ければ上の代替に従う。

`doc/` の置き場所と OKF の規則は `ddd-bdd-tdd-flow` に従う。**本スキルで新しい設計文書の種類を作らない。**

---

## 全体像

```
0 憲章の確認 → 1 入口（唯一の対話）→ 2 仕様合議 → 3 ddd-bdd-tdd-flow（autonomous）
  → 4 網羅ゲート → 5 独立検証 → 7 最終報告
           ↑ 6 監督（全ステージを通して、停滞したら 1 回だけ再開）
```

**人と話すのはステージ 1 と 7 だけ。** ステージ 1 の終わりに「ここから先は質問しません」と宣言する。

## 絶対規則

1. **書かれていないことは止まる（default deny）。** 憲章が触れていない判断は推測で進めず、停止条件として扱う。
2. **書いた者は採点しない。** 合議の裁定役、critic、verifier は、それぞれ作業役とは別の文脈（サブエージェントか別セッション）で動かす。
3. **テストは実装より先に固定する。** フェーズ 3 の `.feature` とフェーズ 4 のテストは、コミットした時点で **変更禁止、追加だけ可**。
4. **完了は申告ではなくゲートで決める。** `FACTORY_GATES: ... status=GREEN` と verifier の `accepted` の両方が揃ったときだけ完了とする。
5. **監督の再開指示は承認ではない。** 承認ゲートで止まった作業役に「続けて」と送ってはならない（ステージ 6）。
6. **すべての仕様に出どころを付ける。** 出どころの無い仕様は削る。
7. **ブランチはローカルに留める。** マージ、push、公開デプロイはしない。

---

## ステージ 0: 憲章の確認

`.factory/charter.md` を読む。**無ければプリセットから作る。** プリセットの選択は、ステージ 1 の最初の質問として利用者にさせる。

| プリセット | 誰が困るか | 合議の人数 | 網羅の水準 |
|---|---|---|---|
| `personal` 自分用ツール | 自分だけ | 2 役 | 標準 |
| `team` チームで使う | 身近な数人 | 3 役 | 標準 + ミューテーション |
| `public` 外部公開 | 知らない人 | 4 役以上 + 別モデル | 全部 |

憲章に必ず書く項目:

```
TIER: personal | team | public
PROTECTED:            # 自律で触ってはいけない。触る必要が出たら停止
  - 認証・パスワード
  - 個人情報の保存
  - 外部への送信（メール、API への書き込み）
  - 課金
  - 公開デプロイ
  - .factory/**、.claude/**、.agents/**
DEFAULTS:             # 入口で聞かなかったときの既定値
  stack: <例: TypeScript + Vite + SQLite>
  storage: ローカルのみ
  language: 日本語 UI
ARBITER_PRIORITY:     # 合議が割れたときの裁定順
  - 安全
  - 入力の字義に反しない
  - 取り消しやすい
  - 単純
LIMITS:
  max_council_rounds: 2
  max_intake_questions: 10
  max_changed_lines_per_slice: 400
```

**作業役は憲章を編集しない。** 憲章は専門家（エンジニア）が書く、上流の判断である。

## ステージ 1: 入口（唯一の対話）

**書かせずに、選ばせる。** 抽象的な要件を求めない。

### 1a. 自由入力を受け取る

聞くのは 3 つだけ。

- 何を作りたいか（一言でよい）
- **それがあったら助かった、最近の具体的な場面を 1 つ**（いつ、誰が、何をしようとして、何に困ったか）
- プリセット（`personal` / `team` / `public`）

入力は文ごとに番号を振って `doc/increments/<日付>-<名前>/factory/intake.md` に保存する。以降の「出どころ」はこの番号を指す。

### 1b. 仕様の草案を内部で作る

利用者には見せない。`ddd-bdd-tdd-flow` のフェーズ 0〜3 を **下書きとして** 走らせる。対象はコンテキストの判定、Example Mapping（ルール / 具体例 / 疑問）、SUDO の D と O、Gherkin の骨子。

**穴は利用者の言葉からではなく、モデルから機械的に探す。**

- 各集約の状態遷移に、抜けている遷移は無いか
- アクター × ユースケースの全組み合わせ
- 作成 / 閲覧 / 更新 / 削除のどれが抜けているか
- 空の状態、権限、取り消し、上限
- 暗黙要件カタログ（下記）のどの項目が当てはまるか

### 1c. 合議の 1 巡目を回す

ステージ 2 の手順 1〜3 だけを実行する。目的は決めることではなく、**本当に曖昧な所を見つけること**である。

### 1d. 選択式の質問を出す

合議で **割れた** うえで `intent_dependent: true` の論点だけを質問にする。

- 最大 `max_intake_questions` 問。重大度の高い順に選ぶ
- 各問は 2〜4 択。**推奨と既定値を明示する**
- 技術用語を使わない。「〜の場合、どうなってほしいですか？」の形にする
- 選択肢は具体例で書く（「削除したら 30 日間はゴミ箱に残る」のように）

回答が無い、または「おまかせ」と答えた問いは既定値を採る。そして **代わりに決めたこと** として記録する。

**ここで「ここから先は質問しません」と宣言する。**

## ステージ 2: 仕様合議

1 回の入力から作った仕様を、複数のエージェントがレビューして妥当なものに決める。

### 手順 1. 役割を分ける

同じ問いを何度も聞くのではない。**見る観点を変える。**

| 役 | 見ること | 必須になるプリセット |
|---|---|---|
| 利用者の代弁 | 入力の言葉と具体例から外れていないか。膨らみすぎていないか | 全部 |
| テスト設計者 | 検証できない記述、網羅の穴、オラクル（期待値）が無い振る舞い | 全部 |
| ドメインの専門家 | 業界の常識、暗黙要件、用語の揺れ | `team` 以上 |
| critic | 前提の飛躍、抽象の過剰、より単純な代替案 | `public` |
| 別モデルのレビュー役 | 同じモデルの思い込みが相関するのを崩す | `public`（可能なら） |

### 手順 2. 最初は互いに見せない

各役は **他の役の意見を見ずに**、独立して指摘を出す。先に見せると同調が起きる。

### 手順 3. 決まった形式で出す

```yaml
- id: R-<役>-<連番>
  target: <S|U|D|O|feature>:<ファイル>#<見出しまたはシナリオ名>
  finding: <何が問題か、1 文>
  severity: blocker | major | minor
  proposal: <どう直すか、1 文>
  confidence: high | medium | low
  intent_dependent: true | false   # 利用者の頭の中を知らないと決められないか
  source: input:<文番号> | catalog:<IR-番号> | inference
```

保存先は `doc/increments/<日付>-<名前>/factory/council/round-<n>-<役>.md`。

### 手順 4. 集約する

裁定役は合議に参加していない、別の文脈で動かす。

1. **重複をまとめる。** 同じ `target` を指す同じ趣旨の指摘は 1 つにする。
2. **機械で判定できるものは投票しない。** 検証できるか、リンクが切れていないか、ID の接頭辞、Gherkin が実行できるか。これらはゲートで判定する。
3. **全員一致の指摘は反映する。**
4. **割れた指摘は、根拠を示させて 1 巡だけ議論させる。** 往復は `max_council_rounds` まで。
5. **それでも割れたら、裁定役が `ARBITER_PRIORITY` の順で決める。** 多数決は使わない。同じ入力なら同じ結論になるようにする。
6. 割れた論点は `doc/ADR/` に `Proposed` で書く。**少数意見を消さずに残す。** `Accepted` にしてよいのは人間だけ。
7. `intent_dependent: true` のまま割れた論点は、ステージ 1d の質問に回す。入口を過ぎていれば、最終報告の「自信のない判断」に回す。

### 手順 5. 出どころで削る

合議後の仕様の各行（ルール、シナリオ、ユースケース）に `source` を付ける。

- `input:<文番号>` — 利用者が言った
- `catalog:<IR-番号>` — 暗黙要件カタログ
- `inference` — 推測。**最終報告の「代わりに決めたこと」に必ず載せる**

**出どころの無い仕様は削る。** これが、合議で仕様が膨らむのを止めるブレーキである。

## 暗黙要件カタログ

誰も口にしないが、全員が期待していること。言語化の不足を補う効果はここが一番大きい。該当するものはすべて、シナリオとテストにする。

| ID | 要件 |
|---|---|
| IR-01 | どの操作でも落ちない。未処理の例外とコンソールエラーが 0 |
| IR-02 | 保存したデータが消えない。リロード後や再起動後も残る |
| IR-03 | 二重送信、連打、二重起動で重複しない（冪等） |
| IR-04 | 空の状態に案内がある。0 件、初回起動 |
| IR-05 | 長い入力、空白だけ、絵文字、日本語入力（IME 変換中の Enter）で壊れない |
| IR-06 | 不正な入力は、理由が分かる日本語で拒否される |
| IR-07 | 削除などの破壊的な操作には確認か取り消しがある |
| IR-08 | 戻る、再読み込み、別タブで状態が矛盾しない |
| IR-09 | 件数が多くても（例: 1 万件）実用的な速度で動く |
| IR-10 | 日付、時刻、タイムゾーン、全角と半角の数字が正しく扱われる |
| IR-11 | キーボードだけで主要な操作ができる。コントラストが足りている |
| IR-12 | 秘密情報をコード、ログ、URL に出さない |

このカタログは憲章と同じく **専門家が育てる。** 作業役は追記を `doc/questions/open/` で提案するだけにする。

## ステージ 3: ddd-bdd-tdd-flow を autonomous モードで回す

フェーズの順序と成果物は変えない。**ユーザーの承認ゲートだけを、次のものに置き換える。**

| フェーズ | 元のゲート | autonomous での置き換え |
|---|---|---|
| 0 コンテキスト判定 | — | **新しいコンテキストを立てる必要が出たら停止。** S 図に線を足すことは自律ではしない |
| 1 ヒアリング | 利用者への質問 | ステージ 1 の入口と合議の結果を `requirements.md` に転記する |
| 2 SUDO | ユーザーの明示的な承認 | 合議の 2 巡目 + ドキュメント検査が GREEN。記録は `approved-by-council` とし、人間の承認と区別する |
| 3 BDD | ユーザーの明示的な承認 | 同上。加えて網羅ゲートの C1〜C3 が GREEN |
| 4 PBT | — | テストをコミットした時点で **固定**。以降は変更禁止 |
| 5 TDD | — | Red の確認を `prove-test` で機械的に行う（ステージ 5） |
| ADR | ユーザーが `Accepted` に | **`Proposed` のまま残す。** 最終報告で人間に渡す |

### スライスに割る

フェーズ 5 は縦のスライスに割る。

- **スライス 0 は曳光弾（tracer bullet）。** 端から端までつながり、中身はほぼフェイクでよい。
- 以降のスライスは、フェイクを 1 つずつ本物に置き換える。
- 1 スライスの差分は `max_changed_lines_per_slice` 以下にする。

### セッションの使い分け

- **フェーズの中では、同じ作業役のセッションを続ける。** 文脈を保つため。
- **フェーズの境目（コミット地点）では、新しいセッションで始め直してよい。** 状態はすべて `doc/` とステータスファイルにあるので、フェーズ 0 の手順で拾い直せる。

## ステージ 4: 網羅ゲート

「全部試す」は不可能である。代わりに **網羅の基準を定義し、満たしたことを機械で示す。** 次のどれか 1 つでも欠けたら RED とする。

| ID | 基準 | どう確かめるか |
|---|---|---|
| C1 | `use-cases.md` の全ユースケースに `.feature` がある | ドキュメント検査 |
| C2 | 各ユースケースが 5 項目を満たす（正常系 / 境界値 / 異常系 / ルール違反 / 並行・冪等） | シナリオのタグ `@happy @boundary @error @rule @concurrency` を数える |
| C3 | `constraints.md` の全規則と全不変条件に、シナリオとテストが 1 つ以上対応する | 規則 ID ↔ シナリオタグ ↔ テスト名の対応表を検査 |
| C4 | 集約ごとの状態遷移表の全セル（不正な遷移を含む）にテストがある | 遷移表から期待集合を作り、テスト名と突き合わせる |
| C5 | 状態を持つ機能には、モデルに対するステートフル PBT が 1 つ以上ある | テストファイルを検査 |
| C6 | `.feature` の全ステップが実際に実行される。未定義と保留が 0 | Cucumber などの実行結果 |
| C7 | 当てはまる暗黙要件（IR-xx）すべてにテストがある | `catalog:IR-xx` タグを数える |
| C8 | 境界値は glossary の単位と番兵から導出されている | glossary と境界値シナリオを突き合わせる |

シナリオは思いつきで書かない。**モデルから導出する。**

- 状態遷移表 → C4
- 同値分割と境界値 → glossary から
- 設定の組み合わせが 4 つ以上 → ペアワイズ法
- 人が列挙しきれない操作の列 → ステートフル PBT に任せる（C5）

**シナリオの追加は critic にもさせる。** 書いた本人とは別の文脈から、反論の立場で「このモデルが壊れる操作の列」を出させる。

## ステージ 5: 独立検証

### ゲートの出力

ゲートのスクリプトは、最後の行を必ず次の形で出す。**必須の検査が実行できなかったときは GREEN にしない。**

```
FACTORY_GATES: level=<fast|full|deep> status=<GREEN|RED|MISCONFIGURED> passed=<n> failed=<n> failing=<名前> skipped=<名前> misconfigured=<名前>
```

| プリセット | 必須の検査 |
|---|---|
| `personal` | types, lint, unit, integration(PBT), e2e, docs, coverage(C1〜C8) |
| `team` | 上記 + mutation |
| `public` | 上記 + audit + smoke(全画面) + monkey + a11y |

### テストが効いていることを示す

- **prove-test**: 実装の差分だけを戻して、追加したテストが落ちることを確かめる。落ちないテストは無価値で、しかも誤解を招く。
- **ミューテーションテスト**: 実装をわざと壊して、テストが検出するかを測る。カバレッジは必要条件にすぎない。
- **仕様が要らない検査**: 全画面・全ルートのスモーク、ブラウザでのランダム操作（モンキーテスト）、コンソールエラー 0、入力のファジング。

### verifier

作業役とは別の文脈で、差分を最初から読ませる。作業役の説明は渡さない。

1. ゲートを自分で実行し、`FACTORY_GATES` の行を自分で得る
2. prove-test を自分で実行する
3. 固定済みのテストが変更されていないかを確かめる。**変更されていたら却下**
4. 差分がスライスの範囲を超えていないか、`PROTECTED` に触れていないかを確かめる
5. スライスの完了条件を、書かれた文字どおりに確かめる

出力:

```
verdict: accepted | rejected
gates: <自分で得た FACTORY_GATES の行>
test_proves_fix: yes | no | could-not-determine (<理由>)
frozen_tests_modified: yes (<ファイル>) | no
scope: within | exceeded (<何が余分か>)
done_when_met: yes | no (<何がまだ偽か>)
must_fix: <番号付きの一覧、または none>
```

**迷ったら却下する。** 却下の損は実装の 1 往復ぶんにすぎない。誤った受け入れは、確かめていない物を「確かめた」と信じさせる。

## ステージ 6: 監督

`tj-loop` があればそれを使う。無ければ、同じ規則を `/loop` で監督役のセッションに回させる。

- **状態はファイルに置く。** 作業役はステータスファイルに進捗を追記する。監督役は 1 判定につき 1 行、`supervisor-log.md` に書く。監督役は記憶を持たない。
- 起きるたびに判定する:
  - **進行中**（ステータスファイルが動いている）→ 何もしない
  - **停滞**（2 回続けて変化なし、またはエラーで停止）→ 最後の状態を添えて再開指示を **1 回だけ** 送る
  - **承認待ちで停止** → 「続けて」は送らない。**「合議の 2 巡目とドキュメント検査を実行し、GREEN なら `approved-by-council` で進め」** と送る
  - **完了の申告** → ステージ 5 の条件を確かめる。満たしていなければ停滞として扱う
  - **判断が必要**（停止条件に当たった、同じ停滞が再開後も続く、作業役が指示を断った）→ 介入をやめて人間に渡す
  - **状態が読めない** → 完了とみなさない。人間に渡す
- 監督役は **進んでいるか** だけを判断する。中身の妥当性は合議と critic、正しさはゲートが判断する。**3 つの判断を混ぜない。**

## ステージ 7: 最終報告

利用者向け。**技術用語を使わない。** `doc/increments/<日付>-<名前>/factory/report.md` に保存し、本文を利用者に渡す。

```markdown
# <作ったもの> ができました

## できること
<.feature の正常系シナリオを、1 行 1 項目の平易な文で>

## 動かし方
<コマンドは最小限。可能なら「このファイルをダブルクリック」の水準で>

## あなたの代わりに決めたこと
<source: inference と、既定値を採った質問。
 「〜の場合は〜にしました。違えば教えてください」の形で>

## 自信のない判断（3 つまで）
<合議で割れた論点のうち重大度の高い順に。
```

## 停止条件

次のどれかに当たったら、作業を止めて `doc/questions/open/` に問いを置き、ステージ 7 の書式で途中報告する。

- 同じスライスでゲートが 2 回続けて RED
- `MISCONFIGURED` が出た（必須の検査が実行できない）
- `PROTECTED` に触れる必要が出た
- 新しいコンテキストを立てる必要が出た
- 合議が `max_council_rounds` を超えても `blocker` で割れ、裁定ルールでも決まらない
- 固定済みのテストを変えないと先に進めない
- 憲章が触れていない判断が必要になった

止まった項目を、黙って進行中のまま残さない。

## ステータスファイル

`doc/increments/<日付>-<名前>/factory/status.md`。コンテキストのリセットや中断から再開するための唯一の拠り所である。

```
increment: <日付>-<名前>
preset: personal | team | public
stage: 0 | 1 | 2 | 3 | 4 | 5 | 7 | stopped
phase: <ddd-bdd-tdd-flow のフェーズ番号>
slice: <現在 / 全体>
council_round: <n>
intake_questions: <回答済み / 出題数>
last_gates: <FACTORY_GATES の行>
last_verdict: <verifier の verdict>
stop_reason: <停止していれば理由>
```

実行ごとの記録は `factory/runs/<UTC 時刻>-<ステージ>.md` に 1 ファイルずつ書く。共有のログに追記しない。

## よくある失敗

| 失敗 | 影響 | 防止策 |
|---|---|---|
| 利用者に要件を「書かせる」 | 空欄か抽象語だけが返ってくる | 具体的な場面を 1 つ聞き、残りは選ばせる |
| 同じモデルの多数決で仕様を決める | 同じ思い込みのまま満場一致で間違う | 役割を分け、1 巡目は独立、裁定はルールで |
| 合議の指摘をすべて反映する | 仕様が膨らみ、入力から離れる | 出どころの無い仕様は削る |
| 監督役が承認待ちに「続けて」と送る | 実質的な自動承認になる | 承認ゲートでは合議と検査を呼ぶ指示に固定する |
| 作業役の「完了しました」を信じる | 未検証の物が完成品として渡る | ゲートと verifier が揃ったときだけ完了 |
| テストを実装に合わせて書き換える | 緑のテストが何も保証しなくなる | テストは固定。変更が必要なら停止 |
| カバレッジ 100% を網羅とみなす | 実行しただけで、確かめていない | ミューテーションと prove-test で効き目を測る |
| 推測した仕様を報告しない | 利用者が意図との違いに気づけない | `inference` はすべて「代わりに決めたこと」に載せる |
