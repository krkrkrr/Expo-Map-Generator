# 会場マップ・ファクトリー

**入力**: 「<会場図 PDF の URL> を見て、良い感じのマップを作って」程度の 1 文。
**出力**: 当日スマホで使える会場マップ（HTML 1 ファイル）、同じ内容のデータ（`map-data.json`）、利用者向けの報告。

このスキルは `oneshot-factory` の特化版である。**ステージの構成、絶対規則、停止条件、ステータスファイル、最終報告の書式は `oneshot-factory` に従う。** ここには会場マップに固有の部分だけを書く。先に `oneshot-factory` の SKILL.md を読むこと。

## パスと前提スキル

このスキルを呼び出すと、スキルのディレクトリ（Base directory）が渡される。以下ではそれを **`<SKILL_DIR>`** と書く。
スクリプトと参考資料は、作業中のリポジトリではなく `<SKILL_DIR>` の下にある。コマンドでは必ず絶対パスに置き換えて実行する。

| 物 | パス |
|---|---|
| スクリプト | `<SKILL_DIR>/scripts/*.py` |
| 「良い感じ」の定義、データの契約 | `<SKILL_DIR>/references/*.md` |
| oneshot-factory 本体 | `<SKILL_DIR>/../oneshot-factory/SKILL.md` |

前提スキルは同じプラグインに同梱している: `oneshot-factory`、`ddd-bdd-tdd-flow`、`external-api-tos-check`、`unresolved-questions`、`okf-open-knowledge-format`、`playwright-test`、`adr-writing-ja`。

Python は、Linux と macOS では `python3`、Windows では `py` で呼ぶ。以下の例は `python3` で書く。

## 「良い感じ」の定義

`<SKILL_DIR>/references/good-map.md` の GM-01〜GM-30 である。利用者の「良い感じ」は、ここに書いた具体的な性質に読み替える。

- 過去に実際の展示会で使った会場マップから書き起こした基準である。元のファイルを探したり真似たりしない
- 仕様合議では、oneshot-factory の暗黙要件カタログ（IR-xx）と同じ扱いの **2 つ目のカタログ** として使う（`source: catalog:GM-xx`）
- GM にも IR にも入力にも出どころが無い機能は足さない

## このスキルが解く問題

会場マップの成果物は **アプリ** と **データ** に分かれる。性質が違うので、別のやり方で品質を担保する。

| | アプリ（検索、地図操作、印付け、保存） | データ（誰がどこにいるか） |
|---|---|---|
| 変わり方 | イベントが変わってもほぼ同じ | イベントごとに全部違う |
| バグの種類 | 実装のバグ | **位置の誤り**（違う区画を指す）と **取りこぼし** |
| 担保の仕方 | ddd-bdd-tdd-flow + ゲート（1 回作れば再利用） | 機械照合 + 画像での確認 + 抜き取り検査（毎回） |

**2 回目以降はアプリを作り直さない。** リポジトリに検証済みのアプリがあれば、データだけを差し替える（ステージ 5）。

## 置き場所

| 物 | 場所 | git |
|---|---|---|
| アプリのソース | `app/` | 入れる |
| 完成品 | `dist/<slug>_map.html`、`dist/<slug>_map-data.json` | 入れない（主催者の著作物を含む。配るかは人が決める） |
| 作業の素材（PDF、ページ画像、layout.json、照合結果、切り出し画像） | `work/<slug>/` | 入れない |
| 仕様、合議、報告、ステータス | `doc/increments/<日付>-<slug>/factory/`（oneshot-factory と同じ） | 入れる |

`<slug>` はイベント名と年から作る（例: `interbee2026`）。`work/` と `dist/` が `.gitignore` に無ければ足す。

## 道具（`<SKILL_DIR>/scripts/`）

| スクリプト | 役割 |
|---|---|
| `extract_pdf.py <pdf か URL> work/<slug>` | ページ画像、ブース候補の矩形、文字のラベル、ブース番号を `layout.json` に。番号が図形で描かれていれば OCR する |
| `match_booths.py --layout … --exhibitors … [--overrides …] --out … --report …` | 出展者と位置の照合。番号 → 社名の順。要確認と未照合を Markdown で報告 |
| `crop.py <pdf> <page> x y w h out.png --mark` | 会場図の一部を切り出す。**照合を目で確かめるときに使う**（画像を Read で読む） |
| `check_data.py dist/<slug>_map-data.json --layout … --min-coverage …` | データの契約の検査（ゲート `level=data`） |
| `smoke.py dist/<slug>_map.html dist/<slug>_map-data.json` | 実ブラウザでの、仕様が無くても言える検査（ゲート `level=smoke`） |

| `setup_check.py [--install]` | 依存（pymupdf、playwright、tesseract、ブラウザ）の有無を調べる。`--install` で入れられるものを入れ、入れられないものは OS ごとのコマンドを出す |

**ステージ 0 の前に `setup_check.py` を実行する。** 依存が欠けたまま進めない。
`--install` で入らない依存（権限、ネットワークの制限）が残ったら、利用者に出たコマンドを渡す。入るまで、その依存を使うゲートは `MISCONFIGURED` であり、GREEN にしない。

## ステージ 0: 憲章

`.factory/charter.md` が無ければ、oneshot-factory のプリセットに次を足して作る。

```
DEFAULTS:
  stack: TypeScript + Vite + vite-plugin-singlefile（HTML 1 ファイルに出す）
  test: Vitest + fast-check（単体・PBT）、Playwright（e2e）
  storage: localStorage のみ
  language: 日本語 UI
MAP:
  min_coverage: 0.90          # 位置が付いた出展者の割合の下限
  audit_sample: 30            # 位置の抜き取り検査の件数
  audit_max_errors: 1         # 抜き取りで許す誤りの数
  page_image_width: 2400      # ページ画像の横幅 px（拡大しても読める）
PROTECTED に追加:
  - dist/ の公開、アップロード
  - ログインが要るページからの取得
```

## ステージ 1: 入口（唯一の対話）

oneshot-factory のステージ 1 と同じ手順で進める。ただし **質問の前に素材を下見する。** 選択肢を具体的にするためである。

### 1a. 受け取る

入力の文を番号付きで `intake.md` に保存する。URL はそのまま記録する。

### 1b. 下見（利用者には見せない）

1. `extract_pdf.py` で会場図を取り込む。ページ数、ホールの名前、凡例、ゾーンの名前を把握する。ページ画像を 1 枚ずつ Read で見る
2. 公式の出展者リストを探す。会場図の URL のドメインと、イベント名で検索する。**取りに行く前に `external-api-tos-check` で利用規約と robots.txt を確かめる。** 禁止されていれば取らない。その場合は会場図の文字だけで作る（2c）
3. 出展者リストのカテゴリ、部門、出展説明を眺め、**注目ジャンルの候補を 3〜5 個** 作る。カテゴリの粒度ではなく、来場者が「これを見に行く」と言う単位にする

### 1c. 質問（AskUserQuestion、最大 4 問、すべて選択式）

| 問 | 選択肢の例 | 既定値 |
|---|---|---|
| 主に使う場面は？ | 当日スマホで回る / 前日に机で計画する / 両方 | 両方 |
| 特に見たいジャンルは？（複数可） | 1b の候補 3〜4 個。「特になし（全社を同じに扱う）」 | 特になし |
| 会場で現在地を出したい？ | 要らない / 出したい（屋内はずれるので手で補正する前提） | 要らない |
| 誰が使う？ | 自分だけ（personal）/ チームで（team） | personal |

- 「特になし」なら GM-23〜27 は作らない。ジャンルを選んだら、その言葉を `intake.md` に記録する（テーマ付けの出どころになる）
- `public`（外部公開）は選択肢に出さない。会場図は主催者の著作物で、公開は人が判断することである
- **ここで「ここから先は質問しません」と宣言する。**

## ステージ 2: データを集める

`work/<slug>/exhibitors.json` を作る。各社に `id, name, booth, hall, division, zone, description, url, logo` を、取れた範囲で入れる。

- **2a. 公式リストがある**: 一覧と詳細を取得する。サーバーに負荷をかけない（1 秒以上の間隔、同時接続 1）。取得した URL と日時を `sources` に残す
- **2b. 略称を足す**: 会場図には略称（「アシダ」=「アシダ音響（株）」）や英語表記が出る。照合の前に、明らかな別表記を `aliases` に入れてよい。出どころは公式の表記に限る
- **2c. 公式リストが無い、取れない**: `layout.json` のラベルを出展者として扱う。`id` は連番、`name` は会場図の表記、`map_note` に「会場図の表記のみ」と書く。報告の「やらなかったこと」に載せる

## ステージ 3: 位置を合わせる

```
python3 <SKILL_DIR>/scripts/match_booths.py --layout work/<slug>/layout.json \
  --exhibitors work/<slug>/exhibitors.json --overrides work/<slug>/overrides.json \
  --out work/<slug>/mapped.json --report work/<slug>/match_report.md
```

`match_report.md` の **要確認** と **未照合** を、1 件ずつ画像で確かめる。

1. `crop.py … --mark` で、照合した区画を赤枠で囲んで切り出し、Read で見る
2. 判断を `overrides.json` に書き、`note` に **何を見てそう決めたか** を残す
   - 社名が区画の外にあり、**引き出し線** で区画を指している → 線の先の区画にする
   - 番号の無い隣の区画も同じ会社の色・枠 → `extra` に足し、`inferred: true` と `booth_note` を付ける（GM-19）
   - 会場図に見当たらない → `null`（位置なし）と、理由を `map_note` に
   - 2 か所に出展している（同じ社名が別ホールにもある）→ 出展者リストのブース番号に合う方を採る
3. 照合を再実行する。`overrides.json` が増えるだけで、`match_booths.py` は書き換えない

**ゾーン**（パビリオン、共同出展エリア）は、凡例やゾーンの一覧表から `zones` を作る。中の会社の位置が個別に分からなくても、ゾーンに入っていれば地図から辿れる。

### 位置の抜き取り検査（書いた者は採点しない）

位置を合わせた作業役とは **別のサブエージェント** に、位置の付いた出展者から無作為に `audit_sample` 件を選ばせる。各件を `crop.py --mark` で切り出させ、「赤枠の区画は、この社名の区画か」を判定させる。照合の方法とスコアは渡さない。

- 誤りが `audit_max_errors` 以下なら合格。誤りの件は直す
- 超えたら、誤りの傾向（OCR の誤読、略称の取り違え、引き出し線）を調べ、全件を見直してから **新しい標本で** やり直す。2 回続けて不合格なら停止条件

参考値: Inter BEE 2026 の会場図（3 ページ、出展 549 社）では、機械照合だけで位置が付いたのは 96%（OCR の番号 400、文字の番号 48、社名 81）だった。手作業の正解と比べると、一致 461 件、食い違い 19 件、位置なし 12 件（対象 492 件）。食い違いの大半は引き出し線の先の小区画である。**機械照合の結果をそのまま出さない理由はこれである。**

## ステージ 4: テーマ付け（注目ジャンルを選んだときだけ）

出展者ごとに、どのジャンルに当たるか、ジャンル別の優先度 S/A/B/C、理由の一言、根拠を付ける（GM-24〜27）。

- **2 つのサブエージェントに、互いの結果を見せずに** 同じ出展者を付けさせる。基準は全員に同じ文面で渡す:
  - S: そのジャンルの主役の製品や実演が、出展説明に名指しで書かれている
  - A: 関連する製品や実演が具体的に書かれている
  - B: 関連はあるが周辺的、または記載が薄い
  - C: カテゴリに登録されているだけ（GM-27）
- 根拠（`evidence`）は出展説明やカテゴリからの引用に限る。**推測で上げない**
- 2 つが一致したものは採る。割れたものは裁定役が根拠の強い方を採る。それでも決まらなければ **低い方** にする（`ARBITER_PRIORITY` の「取り消しやすい」）
- 優先度の分布（S が何社か）を報告に載せる。S が全体の 1 割を超えたら基準が甘い疑いがあり、見直す

## ステージ 5: アプリ

### `app/` が無い（初回）

oneshot-factory のステージ 2〜5 をそのまま回す（ddd-bdd-tdd-flow の autonomous モード）。

- 仕様の材料は `<SKILL_DIR>/references/good-map.md`（GM カタログ）、`<SKILL_DIR>/references/data-contract.md`、入口の回答
- 境界づけられたコンテキストは「会場マップ」の 1 つ。データの取り込み（ステージ 2〜4）はアプリの外の作業であり、アプリはデータを読むだけ
- アプリは `map-data.json` とページ画像を受け取り、HTML 1 ファイルを出すビルドを持つ（`npm run build -- --data … --images … --out …` のような形）
- テスト用の目印（data-contract.md の 2 章）を最初のスライスから入れる。`smoke.py` は曳光弾のスライスから回す
- 網羅ゲートの C1〜C8 に加え、該当する GM-xx すべてにテストがあることを数える（C7 と同じ数え方で `catalog:GM-xx` タグ）

### `app/` がある（2 回目以降）

1. アプリのゲートを今のまま実行して GREEN を確かめる。RED なら先にそれを直す（新しい increment として）
2. 入口の回答が、アプリにまだ無い機能を求めていれば（例: 初めて GPS を選んだ）、その機能だけを oneshot-factory の手順で足す
3. 新しいデータでビルドする。**データの都合でアプリを書き換えない。** データが契約に合わないなら、データの側を直す

## ステージ 6: ゲート

次をすべて実行し、oneshot-factory の `FACTORY_GATES` 行にまとめる。どれかが RED か MISCONFIGURED なら、全体も GREEN にしない。

| 検査 | コマンド | 必須 |
|---|---|---|
| データ | `check_data.py dist/<slug>_map-data.json --layout work/<slug>/layout.json --min-coverage <min_coverage>` | 全プリセット |
| 抜き取り | ステージ 3 の結果（`audit: n=30 errors=0 status=GREEN` の形で記録） | 全プリセット |
| ブラウザ | `smoke.py dist/<slug>_map.html dist/<slug>_map-data.json` | 全プリセット |
| アプリ | `app/` の types, lint, unit, PBT, e2e, 網羅（C1〜C8 + GM） | 全プリセット |
| ミューテーション | `app/` の mutation | team |

## ステージ 7: 最終報告

oneshot-factory の書式に従う。会場マップでは次を必ず入れる。

- **開き方**: 「`dist/<slug>_map.html` をスマホに送って開く」の水準で。ファイルの送り方（AirDrop、自分宛てのメール、クラウドドライブ）を 1 行で。GPS を入れたなら、HTTPS で開かないと動かない場合があることも
- **地図に載せた数**: 「549 社のうち 529 社を地図に載せました。うち 23 社は位置を推定で補いました（地図上で点線、詳細に理由）。20 社は会場図で見つけられず、一覧にだけ載せています」の形で
- **あなたの代わりに決めたこと**: 入口で既定値を採った問い、テーマ付けの基準
- **自信のない判断**: 抜き取りで見つかった誤りの傾向、2 か所に出展していて片方を選んだ会社
- **配布の注意**: 会場図と出展者情報は主催者のものなので、個人やチームでの利用にとどめ、Web に公開しないこと

## よくある失敗

| 失敗 | 影響 | 防止策 |
|---|---|---|
| 照合の結果を見ずに出す | 違う区画を指す。利用者は会場で迷う | 要確認を全件画像で見る。別の文脈で抜き取り検査 |
| 会場図を図形で描き直す | 位置や形がずれ、主催者の図と食い違う | 会場図の画像を背景にし、上に重ねるだけ（GM-01） |
| 位置が分からない会社を一覧から消す | 「あの会社が無い」と利用者が誤解する | 消さずに「マップ位置なし」と理由を出す（GM-20） |
| テーマの優先度を推測で上げる | S だらけになり、絞り込みが効かない | 根拠は引用に限る。分布を報告する |
| イベントごとにアプリを作り直す | 毎回テストからやり直しになり、品質が揺れる | 2 回目以降はデータだけ差し替える |
| 公式サイトを短時間に大量に取得する | 相手の迷惑、遮断 | 規約を確認し、間隔を空け、同時接続 1 |
| 完成品を公開の場所に置く | 主催者の著作物を無断で配ることになる | `dist/` は git に入れず、公開は `PROTECTED` |
